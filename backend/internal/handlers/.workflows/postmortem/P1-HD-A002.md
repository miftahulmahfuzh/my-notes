# Postmortem Report: P1-HD-A002

## Executive Summary
**Problem**: Chrome extension authentication failed with two sequential issues:
1. 401 Unauthorized error due to incorrect token validation method when calling Google's tokeninfo endpoint
2. 500 Internal Server Error due to duplicate key constraint violation when creating/updating users

**Impact**: High - All Chrome extension users unable to authenticate, completely blocking access to multi-device note synchronization feature.

**Resolution**:
1. Fixed token validation to use query parameter instead of Authorization header
2. Fixed user upsert logic to query by email (unique constraint) instead of google_id

**Duration**: ~45 minutes from initial error identification to complete resolution of both issues

## Timeline

### Discovery
- **Time**: 2025-02-06
- **Method**: User reported 401 Unauthorized error when attempting to authenticate via Chrome extension
- **Initial Symptoms**:
  - Console logs showed `chrome.identity.getAuthToken()` successfully returned a token
  - Backend API call to `/api/v1/auth/chrome` returned 401 status
  - Error response: `{"success":false,"error":{"code":"UNAUTHORIZED","message":"Invalid Chrome token","details":"token validation failed with status: 400, response: { \"error_description\": \"Invalid Value\" }"}}`

### Investigation
- **Time**: 2025-02-06
- **Methods**:
  - Analyzed frontend auth flow in `extension/src/auth.ts`
  - Examined backend Chrome auth handler in `backend/internal/handlers/chrome_auth.go`
  - Researched Google's tokeninfo endpoint documentation via Context7 and web search
  - Compared Chrome Identity API token handling with standard OAuth 2.0 practices
- **Key Findings**:
  - Frontend correctly obtained OAuth token using `chrome.identity.getAuthToken()`
  - Backend used `Authorization: Bearer <token>` header to call `https://www.googleapis.com/oauth2/v2/tokeninfo`
  - Google's `tokeninfo` endpoint specifically expects `access_token` as a **query parameter**, not in the Authorization header
  - The `Authorization: Bearer` header method is standard for most Google APIs but NOT for the tokeninfo endpoint itself

### Resolution
- **Time**: 2025-02-06
- **Approach**: Changed from Authorization header to query parameter method for tokeninfo endpoint calls
- **Implementation**:
  - Updated `chrome_auth.go` to construct URL with query parameter: `https://oauth2.googleapis.com/tokeninfo?access_token=<token>`
  - Added `net/url` import for proper URL encoding of the token
  - Also upgraded from deprecated `v2` endpoint to current `oauth2.googleapis.com` endpoint
  - Rebuilt and tested backend successfully

### Issue 2 Discovery (After Initial Fix)
- **Time**: 2025-02-06 (after Issue 1 resolution)
- **Method**: User re-tested authentication after token validation fix
- **Initial Symptoms**:
  - Token validation now succeeded (Issue 1 resolved)
  - Backend API call to `/api/v1/auth/chrome` returned 500 status
  - Error response: `{"success":false,"error":{"code":"INTERNAL_ERROR","message":"Failed to create user","details":"failed to create or update user: failed to create user: pq: duplicate key value violates unique constraint \"users_email_key\""}}`

### Issue 2 Investigation
- **Time**: 2025-02-06
- **Methods**:
  - Analyzed user service `CreateOrUpdateFromGoogle` method in `backend/internal/services/user_service.go`
  - Examined database schema for unique constraints
  - Traced data flow from Chrome auth handler to user service
- **Key Findings**:
  - `CreateOrUpdateFromGoogle` queried users by `google_id` (line 49)
  - Chrome auth fallback ID generation (line 204 in `chrome_auth.go`) creates inconsistent IDs: `"chrome-user-" + email`
  - When user existed with a different `google_id`, query returned no rows
  - Code attempted INSERT which failed due to unique constraint on `email` column
  - The `email` column has a UNIQUE constraint (confirmed in `001_create_users_table.up.sql`)

### Issue 2 Resolution
- **Time**: 2025-02-06
- **Approach**: Changed upsert logic to query by email (the unique constraint) instead of google_id
- **Implementation**:
  - Updated `CreateOrUpdateFromGoogle` to query by `email` first
  - When updating existing user, also update `google_id` (it can change from fallback to real ID)
  - Updated `updateUser` helper to include `google_id` in the UPDATE statement
  - Rebuilt backend successfully

## Problem Analysis

### Issue 1: Token Validation Method (RESOLVED)

### Root Cause Analysis
**Primary Cause**: The Chrome authentication handler was using the wrong method to pass the access token to Google's tokeninfo endpoint.

**Technical Root Cause**:
```go
// BEFORE (Incorrect)
tokenInfoURL := "https://www.googleapis.com/oauth2/v2/tokeninfo"
req, err := http.NewRequest("GET", tokenInfoURL, nil)
req.Header.Set("Authorization", "Bearer "+token)
```

The tokeninfo endpoint expects:
```go
// AFTER (Correct)
tokenInfoURL := fmt.Sprintf("https://oauth2.googleapis.com/tokeninfo?access_token=%s", url.QueryEscape(token))
req, err := http.NewRequest("GET", tokenInfoURL, nil)
```

**Contributing Factors**:
- **API Documentation Confusion**: Most Google APIs use the `Authorization: Bearer` header method per RFC 6750, making the tokeninfo endpoint's exception non-obvious
- **Endpoint Version**: Using deprecated `oauth2/v2/tokeninfo` endpoint instead of current `oauth2.googleapis.com/tokeninfo`
- **Lack of Specific Testing**: The token validation code path was not tested with actual Chrome Identity API tokens

### Technical Details
**Affected Component**: `backend/internal/handlers/chrome_auth.go:138-145`

**Error Flow**:
1. Frontend calls `chrome.identity.getAuthToken()` → receives valid token
2. Frontend sends token to backend `/api/v1/auth/chrome`
3. Backend calls Google's tokeninfo endpoint with `Authorization: Bearer <token>` header
4. Google's tokeninfo endpoint returns 400 Bad Request with "Invalid Value"
5. Backend interprets this as invalid token → returns 401 to frontend

**Failure Mode**: Authentication completely broken for all Chrome extension users

### Issue 2: User Upsert Logic (RESOLVED)

**Primary Cause**: The `CreateOrUpdateFromGoogle` method queried by `google_id` but the unique constraint is on `email`. When a user's `google_id` changed (e.g., from fallback ID), the query returned no results and attempted to INSERT, violating the email unique constraint.

**Technical Root Cause**:
```go
// BEFORE (Incorrect)
// Query by google_id - but google_id can change!
err := s.db.QueryRowContext(ctx,
    `SELECT id, google_id, email, avatar_url, created_at, updated_at
     FROM users WHERE google_id = $1`,
    userInfo.ID).Scan(...)
```

The correct approach queries by email (the unique constraint):
```go
// AFTER (Correct)
// Query by email - the column with UNIQUE constraint
err := s.db.QueryRowContext(ctx,
    `SELECT id, google_id, email, avatar_url, created_at, updated_at
     FROM users WHERE email = $1`,
    userInfo.Email).Scan(...)
```

**Contributing Factors**:
- **Inconsistent google_id Generation**: Chrome auth fallback generates `"chrome-user-" + email` when real Google ID is missing
- **Mismatched Query Key**: Query used `google_id` as key, but unique constraint is on `email`
- **No google_id Update**: When user existed, update didn't refresh `google_id` in case it changed

**Affected Component**: `backend/internal/services/user_service.go:42-83`

**Error Flow**:
1. User previously authenticated with `google_id` value A (e.g., fallback ID)
2. User re-authenticates, receives `google_id` value B (e.g., real Google ID)
3. `CreateOrUpdateFromGoogle` queries by `google_id` = B
4. Query returns no rows (user has ID A stored)
5. Code attempts INSERT with same email
6. Database rejects INSERT due to unique constraint on email
7. 500 error returned to frontend

**Failure Mode**: Authentication failed for returning users whose `google_id` value changed between sessions

## Resolution Details

### Solution Strategy
**Approach Rationale**:
- Google's tokeninfo endpoint is specifically designed for debugging/validation
- Unlike other Google APIs, it expects the token as a query parameter
- This is documented behavior but not immediately obvious from standard OAuth 2.0 practices

**Alternative approaches considered**:
- Using Authorization header: Does not work with tokeninfo endpoint (proven by this incident)
- Switching to JWT verification libraries: More complex, requires additional dependencies
- Using userinfo endpoint instead: Returns different data structure, would require more code changes

### Implementation Details

**Code Changes**:

```go
// BEFORE: Using Authorization header (incorrect for tokeninfo endpoint)
tokenInfoURL := "https://www.googleapis.com/oauth2/v2/tokeninfo"
req, err := http.NewRequest("GET", tokenInfoURL, nil)
if err != nil {
    return nil, fmt.Errorf("failed to create tokeninfo request: %w", err)
}
req.Header.Set("Authorization", "Bearer "+token)

// AFTER: Using query parameter (correct method)
tokenInfoURL := fmt.Sprintf("https://oauth2.googleapis.com/tokeninfo?access_token=%s", url.QueryEscape(token))
req, err := http.NewRequest("GET", tokenInfoURL, nil)
if err != nil {
    return nil, fmt.Errorf("failed to create tokeninfo request: %w", err)
}
```

**Additional Changes**:
- Added `net/url` import for `url.QueryEscape()` function
- Upgraded from `oauth2/v2/tokeninfo` to `oauth2.googleapis.com/tokeninfo` (current endpoint)

**Files Modified**:
- `backend/internal/handlers/chrome_auth.go` - Updated `validateChromeToken()` method (Issue 1)
- `backend/internal/services/user_service.go` - Updated `CreateOrUpdateFromGoogle()` and `updateUser()` methods (Issue 2)

### Issue 2 Implementation Details

**Code Changes**:

```go
// BEFORE: Query by google_id (can change, causes duplicate key error)
err := s.db.QueryRowContext(ctx,
    `SELECT id, google_id, email, avatar_url, created_at, updated_at
     FROM users WHERE google_id = $1`,
    userInfo.ID).Scan(...)

// AFTER: Query by email (unique constraint, reliable lookup)
err := s.db.QueryRowContext(ctx,
    `SELECT id, google_id, email, avatar_url, created_at, updated_at
     FROM users WHERE email = $1`,
    userInfo.Email).Scan(...)
```

**Additional Changes**:
- Update existing user's `google_id` when it changes (e.g., from fallback to real ID)
- Updated `updateUser()` helper to include `google_id` in UPDATE statement:
```go
// BEFORE: Only update avatar_url
UPDATE users SET avatar_url = $1, updated_at = $2 WHERE id = $3

// AFTER: Also update google_id
UPDATE users SET google_id = $1, avatar_url = $2, updated_at = $3 WHERE id = $4
```

## Lessons Learned

### Technical Insights
**What We Learned**:
- Google's tokeninfo endpoint is an exception to the standard OAuth 2.0 `Authorization: Bearer` header pattern
- The tokeninfo endpoint specifically requires `access_token` as a query parameter
- Most OAuth 2.0 endpoints use Authorization headers, but debugging/validation endpoints sometimes differ
- The `oauth2/v2/tokeninfo` endpoint is deprecated; current endpoint is `oauth2.googleapis.com/tokeninfo`
- **User upsert logic must query by the unique constraint column**, not by mutable identifiers
- **Fallback ID generation** (e.g., `"chrome-user-" + email`) creates inconsistent identifiers across sessions
- **google_id is not a stable primary key** for user lookups - it can change from fallback to real ID

**Best Practices Identified**:
- Always verify the specific API documentation for each Google OAuth endpoint
- Don't assume all OAuth 2.0 endpoints follow the same authentication pattern
- Integration tests can catch API usage errors before production
- **For upsert operations: query by the unique constraint column, not by mutable fields**
- **Be wary of fallback ID generation - creates data consistency issues**
- **Always update all mutable identifier fields when upserting (not just "display" fields)**

### Process Insights
**Development Process**:
- Systematic debugging approach (following debugging skill) led to efficient root cause identification
- Context7 MCP tool and web search were essential for understanding Google's API requirements
- The fix was simple once the root cause was identified

**Knowledge Gaps**:
- Tokeninfo endpoint's non-standard authentication method
- Current vs deprecated Google OAuth endpoint URLs
- User upsert patterns with mutable identifiers (learned through Issue 2)
- Impact of fallback ID generation on data consistency
